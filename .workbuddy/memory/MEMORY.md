# asmr-live-sub 项目长期笔记

## 项目定位
WASAPI 环回去 → faster-whisper(ja) → 中文翻译 → 置顶字幕窗。实时追 ASMR 直播日语字幕。
主文件 `live_sub.py`（单文件，约 900 行）。**不是 git 仓库**，改前手动备份为 `live_sub.py.bak-<时间戳>`。

## 硬件与模型约束（2026-09-20 实测）
- GPU：RTX 4060 Laptop 8GB，日常被桌面占用 ~2.9GB（**可用仅 ~5GB**）
- RAM：32GB；Whisper 跑 CUDA，Sakura 7B 跑 CPU
- 已下载模型：`models/models--Systran--faster-whisper-small`、`models/nllb`(CT2)、`models/sakura/*.gguf`(4GB)、`models/qwen`

## 关键实测数据（09-20 一场）
- ASR 调用 1538 次，其中 **empty 949 次(61.7%)**；KEPT 589
- 丢弃分布：sound-only 650 / hallucination 92 / no-speech 39 / repeat 8 / kana-loop 2
- **段长分布：p10=p25=p50=1.02s**（frame_s=0.51 的两倍，撞帧对齐）
- 段长 vs empty 率：0.8-1.5s→73% / 1.5-3s→54% / 3-6s→42% / >6s→23%
- 翻译延迟(sakura CPU)：p50 0.75s p90 1.48s **max 21.4s**

## 已做的修改（2026-09-20）
1. `hang_s` 0.9 → **2.0**（对齐 faster-whisper Silero `min_silence_duration_ms` 默认 2000ms）
2. 新增模块级常量 `MIN_SEG_S = 1.5`，段长下限 0.8s → 1.5s
3. `drop_reason` 新增 `compression_ratio` 参数，>2.4 判 `repetition`
4. `low-conf` 去掉「必须与 NSP>0.6 同时成立」的 AND 条件（原实现 0 次触发）
5. 加 `patience=2`；layer>=2 时显式传 `vad_parameters`
6. 去重从「只比上一条」改为**最近 5 条历史窗口**（`last_ja` 变 `list[str]`）

验证：`--source-audio smoke90.wav --layer 2` 真实抓出 7 条 low-conf 幻觉。分段器对比同样 60s 素材：段数 11→9，p50 3.57s→7.65s。

## 实盘两轮验证结果（2026-09-20，各 5 分钟）
| 指标 | 旧参数 | 第1轮 | 第2轮(最终) |
|---|---|---|---|
| 段长 p50 | 1.02s | 3.57s | **4.08s** |
| <1.5s 碎片 | 788 (51%) | 0 | **0** |
| empty 率 | 68% | 37% | ~24% |

## low-conf 阈值调参过程（重要经验）
- 初版：`avg_logprob < -1.0` 独立触发 → **误杀严重**。5 分钟内 15 条 low-conf，
  一半是正常句（"ここに乗ってみたら"、"すごい"、"危ないよ"）。
- 加段长门槛 `audio_s > 4.0s` → 降到 3 条，但仍有 2 条误杀：
  `お疲れ様です`(-1.028)、`今のがいいね`(-1.002) —— 正常常用语擦线。
- **最终阈值 `-1.15`**：实测正常段平均 logprob 是 **-0.54 ~ -0.61**，
  被误杀的正常句集中在 -1.00 ~ -1.03，真正的乱码幻觉在 -1.09 以下（但 -1.09 仍太接近）。
  收紧到 -1.15 后，正常句有 0.5 以上的安全边际。
- 教训：**调置信度阈值必须看真实分布，不能照搬论文默认值**。Whisper 官方默认
  `logprob_threshold=-1.0` 是为英文长段调的，日语 ASMR 短句场景完全不适配。

## JSONL 统计口径修复
旧版 `work.jsonl` 的 `drop` 字段只记"整段最终结论"，段内被丢的 segment 原因在
`ja` 非空时**全部丢失**——导致按 JSONL 统计丢弃分布只剩 `empty` 一类，严重失真
（我据此误判过一次）。新增 `seg_drops` 字段汇总逐 segment 原因。

## Segmenter 静音垫 bug（2026-09-20 第三轮挖出，已修）
**现象**：`MIN_SEG_S=1.5` 门槛一直是失效的，形同虚设。
**根因**：`_emit` 把 `hang_frames=3` 帧挂起静音一起打包 → 每段自带 **~1.53s 静音垫**。
哪怕只有 1 帧人声（0.51s），打包后 2.04s，必然越过 1.5s 门槛。
实测 **0.4s 爆音 → 入队段长 2.55s，完全没拦住**。
**连带纠正**：之前以为「<1.5s 碎片 788→0」是门槛生效，其实不然——是 `hang_s` 0.9→2.0
把它们**合并进邻段**了。门槛从头到尾没起作用过。
**修法**：
1. 新增 `self._voiced_frames`，只数真正 voiced 的帧；
2. 门槛改判 `voiced_s = _voiced_frames * frame_s`，不判打包总长；
3. `_emit` 把**尾部挂起静音剪掉再送 ASR**（省算力；也避免静音稀释 `avg_logprob`）
   —— `trail = _silence_run if _silence_run < _speech_frames else 0`，`keep = len(_speech) - trail`。
**验证**：0.4s/0.3s 碎片 → drop；2.5s/4.0s 人声 → 入队（剪静音后 3.06s/4.59s）。

## 踩过的坑
- **`suppress_tokens=""` 在 faster-whisper 下会崩**：它走 ctranslate2，该参数必须是 `List[int]`（默认 `[-1]`）。空串是 OpenAI 原版 whisper CLI 的写法，会抛 `incompatible function arguments`。要关闭用 `[]`。
- **跑脚本必须用项目自带 venv** `.venv\Scripts\python.exe`，不是受管 Python 环境（那边没装 faster_whisper）。`start.bat` 里也是它。

## 社区调研结论（重要，纠正了早期误判）
- **不要用 kotoba-whisper-v2.2**：第三方基准（kuro.boo, MLX）字符匹配率仅 **36.9%**，句子后半段丢失，虽最快但不可用。
- **推荐 `litagin/anime-whisper`**：756M，MIT，HF 月下载 70K+。底座 kotoba-whisper-v2.0，5300h 动漫语音微调。官方特性：Reduced Hallucination、非言语声识别（笑/叹气/呼吸）、**NSFW 内容处理**、13% CER。有 CT2 版 `quantumcookie/anime-whisper-ct2` 可被 faster-whisper 直接加载。⚠️ 官方要求**不加 initial_prompt**。
- **备选 `large-v2`**：多个实测反馈幻觉明显少于 large-v3。
- **不要做降噪/人声分离**：「预处理器悖论」——Whisper 吃 log-Mel 谱，降噪会削掉区分辅音的高频瞬态，反而加剧幻觉。
- 参考项目 **WhisperJAV**（meizhong986，MIT，2035★）：`--sensitivity aggressive` 专为 ASMR 调。设计要点：VAD clamping、句子重组感知终助词(ね/よ/わ/の)与相槌(うん/はい)、sound-only 行删除带「证据检查」防误删、timing repair。

## sentence regrouping：~~已验证为架构上多余~~ ⚠️ **2026-09-22 论据已推翻，待重新评估**
**原结论：不要做。** 原因链：
1. `Segmenter` 在**音频层**已经做了"按停顿合并"
2. `hang_s=2.0` 意味着 <2s 的停顿根本不产生新段
3. ~~所以送进 ASR 的段，段间间隔**恒 >= 2.0s**（实测 2.50/2.60/2.60/3.00s）~~
   🔴 **此条已被证伪（2026-09-22）**：那是 **4 个样本**得出的。517 个间隔实测
   **p10=0.50 p50=0.50 p90=5.10 min=0.50**（秒）。存在大量 0.50s（≈1 帧）的紧邻段，
   它们正是 `max_s=8.0` 硬切产生的"半句对"。
4. 因此任何靠"段间隔"判断重组的规则必然二选一：
   - 阈值 < 2.0 → 永不触发（等于没写）
   - 阈值 > 2.0 → 把独立句也并进来（正是旧版的错误）
   **（第 4 条同样建立在第 3 条之上，前提没了，推论失效。）**

🔴 **2026-09-22 新增：真正的根因在音频层，不在文本层**
`max_s=8.0` → `max_frames = int(8.0/0.51) = 15` = **7.65s**。
会话 #25 实测 `audio_s` p50 = **7.65s**，且 **62.3% 的段 audio_s >= 7.0s**
=> **六成以上的段边界是 max_s 人为硬切的**，落在词中间。实例：
```
seg4  audio_s=3.06  ja=母校人の少子化対策だからって
seg5  audio_s=4.08  ja=子作りの相手が勝手に選ばれるなんて、すごいよ   (gap=0.50s)
```
连读是一句话。识别出半句 → 翻译必然错（`奏でいらっしゃい`→`奏请自重` 同源）。
**=> 修 max_s 的切法比回文本层做重组更彻底。** 帧对齐（0.51s）只是次级因素。

附：`hang_frames = int(2.0/0.51) = 3 帧 = 1.53s`，`hang_s=2.0` 实际只生效 1.53s。

**实测证据**（`test_convo.wav`，11 句、停顿已知，`--replay` 原速过 Segmenter）：
- 设计短停顿 0.4~0.5s 处 → Segmenter **已自动合并**：
  `すごく気持ちいいですよ`+`ね` → 同一段；`うん`+`そうですね、私も…` → 同一段
- 设计长停顿 3.0s 处 → 正确断开（间隔 2.6~3.0s）
- 重组规则跑真实数据 → **合并 0 次**（正确，因为确实没有该合并的）

**旧版 regroup 的"压缩 14.9%"是假的**：它在没有时间戳的日志上瞎猜，
把间隔 5~10s 的独立句也合并了，所以"看起来有效"。

**教训**：`hang_s` 这个音频层参数，和"句重组"这个文本层规则，解决的是同一件事。
先确认哪一层已经做了，再决定要不要在另一层重复做。

| ASR 调用 | 206 | 70 |
| 成功识别 | 36 | **70** |
| 空识别 | 170 | **0** |
| **空识别率** | **82%** | **0%** |

**字幕产出提升 4.7 倍，空识别率从 82% 降到 0%。**

### 根因（同一段实时音频直接对照）
| layer | 结果 |
|---|---|

**注意**：layer 1 下 `sound-only` 丢弃从 1 升到 18 —— 这是**正确**的：
以前这些段被 VAD 提前吃掉了，现在能进到文本层被正常过滤。不是回归。

## 微调可行性核查（2026-09-22，结论：现在不能做，且不一定是真需求）
**三条硬阻塞**：
1. **音频没落盘**。`asr` 事件只有 `audio_s`(时长数字) / `rms`(能量数字)，
   无音频本体、无路径 → 现有数据一条都不能用于 ASR 微调。
2. **`ja` 是模型输出不是标签**。拿它当训练标签 = 自我蒸馏的错误用法，
   只会放大现有错误。真标签必须人工听写，而用户日语 Duolingo ~5，标不了。
3. **错误主要出在分段层而非模型层**。实例：`奏でいらっしゃい` 被 Segmenter
   从词中间切开 → 译文「奏请自重」。输入端信息已丢，微调翻译模型救不回来。

**硬件约束**：CTranslate2 官方明确 inference-only、**不支持训练**；ASR 微调路径是
「HF transformers 格式 LoRA → 转回 CT2」，756M 的 anime-whisper 在 8GB 上可行。
Sakura 7B 的 QLoRA 通常需 10-12GB，本机 8GB 且桌面占 2.9GB、**实际可用 ~5GB → 跑不动**。
参考量级：HF 上 Whisper 匈牙利语 LoRA 案例用了 FLEARS **3502 条带标注**数据。

**数据可用性缺陷**：`work-20260920.jsonl` 里**混了 26 次启动**（按 `start` 事件切分），
配置各异。最有价值的是会话 **#25**（layer1/anime，522 ASR → 368 字幕，空率 29.5%）。
其余多为 1 条 ASR 的 smoke test。=> 当"测试集"用之前，必须先能回答
"这条数据来自哪个配置"，当前做不到。
⚠️ **跨会话指标不可直接比较**：#25 空率 29.5% vs 对照实验的「0%」不矛盾，
音频内容不同（对照那段是连续人声）。

**建议路径**：先做错误分类（从 #25 抽 100 条 ja/zh，分「识别错/翻译错/该显示没显示/都对」
四类），用结果决定后面动哪一层。不需要新代码、新数据、GPU。
若坚持微调，最小可行版：存音频 → 攒 500-1000 条 → 听写 200 条做**评估集**
（先不训练）→ 验证「现在到底错多少」→ 只有系统性错误才考虑训练。

## Segmenter 计数口径 bug + 真瓶颈是延迟（2026-09-22 修正，覆盖先前归因）
**参数是真坏的，但危害被我先夸大了；而且真瓶颈不在这。**

1. `max_s=8.0` **名不副实**：`_speech_frames` 只数有声帧（`live_sub.py:326` 只在
   `if voiced:` 分支 `+=1`，静音帧 append 不计数）。静音只夹 1~2 帧时永远攒不满
   `hang_frames=3`，段一路撑到「有声帧=15」才吐 → 实质是"最多 15 个有声帧"，不是"最多 8 秒"。
   实测 522 段 min 2.04 / p50 7.65 / p90 9.69 / **max 15.30**，**37% 超过 8.0s**。
2. `hang_frames = max(1, int(2.0/0.51)) = 3 帧 = **1.53s**`，`hang_s=2.0` 从未真正生效（取整丢 23%）。
3. **硬推理**：自然断句需 ≥1.53s 静音 → 自然断点间隔必 ≥1.53s。实测 324 对相邻长段中
   **279 对间隔 <1.0s**（大量正好 0.50s = 1 帧）→ 这些断点必为强制。✅
4. ⚠️ **但"62% 的段是半句话"是我的夸大**。以残片开头的段实测**只有 3/522 = 0.6%**；
   ≥7.0s 长段里约一半是连续拟声/喘息流（`じゅるるる…` / `くぷくぷ…`），本就没有"词"可切。
5. 🔴 **真正的 P0 是延迟**：按 `seg_id` join 368 条，**字幕延迟(段首词)=段长+asr+mt**，
   p50 **9.64s** / p90 12.41 / max 16.98。**段长占 79%**、识别 3%、翻译 17%。
   => 先前结论「翻译慢 5.1 倍是瓶颈」**抓错了重点**。字幕不是逐字流，是憋一大块突然蹦出。
6. **取舍（未动手）**：让上限按**墙钟**生效且 `max_s` 降到 4~5s → 延迟 ~5-6s，
   代价是句中切断概率上升。想快就必须更常切句，想准就必须更慢。没有免费午餐。

## 切块定性（2026-09-22 第五轮）：**"慢"的唯一主因，"丢"的不是**

一句话：**切块吃掉 79% 的延迟，但几乎不丢字幕。这两件事必须分开谈。**

### 延迟侧：是它
`live_sub.py:330` 的 `if self._speech_frames >= self.max_frames:` 数的是**有声帧个数**。
=> 凡是被这条规则切开的段，墙钟 **≥ 15 × 0.51 = 7.65s 是下限，不是均值**。
实测 p50 恰好 = 7.65s，62.3% 的段 ≥7.0s。段长分布**双峰**证实两套规则并存：
3-5s 堆（静音自然切，197 段）/ 7-9s 堆（撞上限强制切，239 段）/ 5-7s 谷底。

### 丢弃侧：不是它
154 条空识别段的真实文本绝大多数是纯喘息（`はぁ…はぁ…` / `んぐっ、んぐっ` /
`じゅるるるる…`），**模型没听错，丢掉是对的**。仅找到 **2 条**因"喘息与真话被塞进
同一子段"而陪葬的（`れろれろ…また一緒に…`）。

### 🔴 新事实：ASR 对每段只吐 1 个子段（522/522 全部 nseg=1）
子段 `start=0, end=段长`，覆盖整段。=> 段越长，混进异质内容的机会越大，
却只能整体判一个结论。这是"长段空率更高"的结构性原因。

### 段长 vs 空识别率（**非单调**，别过度解读）
`<4s 15.8% / 4-6s 24.7% / 6-8s 40.6% / 8-10s 26.4% / ≥10s 43.8%`。
趋势是"硬切的长段更容易空"，但 8-10s 桶只有 26.4%，**不是干净的单调关系**。
短段质量更好 → 因为真静音 = 一句真说完了。

### 为什么"必须切"（2026-09-22 第六轮，实测）
1. **Whisper 是 30 秒窗口模型**。180s 音频不做任何切分一次性喂入 → 吐出 6 段，
   起点**精确落在 0.00 / 30.00 / 60.00 / 90.00 / 120.00 / 150.00**，与音频内容无关。
   => 不切不是选项，只是把切点交给模型，在更糟的位置切。**这是唯一真正的硬约束。**
2. **实时性**——不切就要等 30s 才出字幕。
3. **翻译侧不是约束**：`n_ctx=2048`、`max_tokens≤80`，但 `completion_tokens` p50 只有 10，
   仅 1/368 撞上限（还是退化输出）。别拿它当理由。

### ⭐ 真根因：能量阈值分不清"说话"与"喘气"
实测语速（保留段）：**2-4s 段 3.85 字/秒 → 10-16s 段 2.12 字/秒**，
全部平均只有 **2.59 字/秒**（正常日语 6-8，ASMR 慢速 4-5）。
**段长 ×3.8 而字数只 ×2.1 —— 拉长的部分主要是喘息，不含信息。**

链：阈值 0.008 太低 → 呼吸/底噪算作"有声帧" → 15 帧配额被喘息占满 → 段必然撑到 7.65s
→ 静音规则①需 1.53s 完全安静、ASMR 里难出现 → ①只占 37.7%、②占 60.3%
→ **79% 的延迟是"等喘息填满配额"，不是"等一句话说完"**。

=> 真问题不是"要不要切"，而是**"凭什么判断这一块说完了"**。现在判据是能量，
而能量区分不了说话和喘气，所以切点与语义无关。

### 两套规则归属（用 `audio_s` 可精确判定）
规则② → `audio_s ≥ 15×0.51 = 7.65s`；规则① → `_speech_frames<15` → `audio_s ≤ 7.14s`。
实测 522 段：**② 315 段 (60.3%) / ① 197 段 (37.7%) / 中间带 10 段 (1.9%)**。
**兜底规则成了主力。**
