## 用户真问题：要不要自己收集测试集 / 做微调

### 决定性发现 1：数据里根本没有音频
`asr` 事件完整字段：

`audio_s` 是时长数字，`rms` 是能量数字，**没有任何地方把音频落盘**。

### 决定性发现 2：`ja` 不是标签，是模型自己的答案
`ja` = anime-whisper 的输出。拿它当训练标签去训同一模型 = 自我蒸馏的错误用法，

### 🔴 重大发现：max_s 硬切是主要切段方式，不是静音
会话 #25（layer1/anime）实测：

| 指标 | 值 |
|---|---|
| `audio_s` p10 / **p50** / p90 / max | 3.06 / **7.65** / 9.69 / 15.30 |
| `audio_s >= 7.0s` 的段 | **325 / 522 = 62.3%** |

**7.65s = 15 帧 × 0.51s = `max_frames`（int(8.0/0.51)=15）。**
=> 62.3% 的段是被 `max_s=8.0` 强制切断的，**段边界落在词中间**。

直接实例（连续两条，gap=0.50s）：
```

seg5  t=[62.70, 67.80]  audio_s=4.08  ja=子作りの相手が勝手に選ばれるなんて、すごいよ
```
两句连读语法完整、语义连贯，**是一句话被切开**。识别出半句 → 翻译必然错。

还有一个同源 bug：`hang_frames = int(2.0/0.51) = **3 帧 = 1.53s**`，
所以 `hang_s=2.0` 实际只有 1.53s 生效（取整丢了 23%）。

**这推翻了之前"0.51s 帧对齐切词"的归因**——帧对齐只是次级因素，主因是 max_s 硬切。

### 修正 2：max_s=8.0 根本没生效
不是"8 秒硬切"。`_speech_frames` **只数有声帧**（`live_sub.py:326` 只在 `if voiced:`
分支里 `+= 1`；静音帧 append 但 `_speech_frames` 不动）。所以：
- 只要静音每次只夹 1~2 帧（0.51~1.02s），永远攒不满 `hang_frames=3` → 自然断句不触发
- 段一路撑到「有声帧 = 15」才吐 → 墙钟远超 8s

实测 522 段：min 2.04 / p50 7.65 / p90 9.69 / **max 15.30**，**195 段（37%）超过 8.0s**。
`max_s=8.0` 名不副实，管的是「最多 15 个有声帧」。

### 「这些断点必为强制」的硬推理 ✅
自然断句需连续 3 帧静音（>=1.53s）→ **自然断开的段，间隔必 >=1.53s**。
实测 324 对相邻段（前段 >=7.0s）中，**279 对（86%）间隔 < 1.0s**，大量正好 0.50s
（= 1 帧静音）。1 帧静音不可能触发自然断句 → 断点必为强制。

### 🔴 真正的问题：字幕延迟 ~9.6 秒（此前完全没提）
按 `seg_id` join `asr` 与 `mt`（368 条配对）：**延迟 = 段长 + asr_s + mt_s**

| 组成 | p50 | 占比 |
|---|---|---|
| **等段攒满（段长）** | **7.65s** | **79%** |
| 识别 asr | 0.32s | 3% |
| 翻译 mt | 1.63s | 17% |
| **合计** | **9.64s** | |

p10=4.55 / p50=9.64 / p90=12.41 / **max=16.98s**。

=> 说完一句要等近 10 秒才出中文；且**不是逐字流，是憋一大块突然蹦出**
（段首词等 9.6s，段尾词只等 ~2s）。
**上一节把重点放在「翻译慢 5.1 倍」是抓错了**——翻译 1.6s 只占 9.6s 的 17%。

## 切块定性：是"慢"的唯一主因，**不是**"丢"的主因（2026-09-22 第五轮）

用户问「主要卡点是不是在切块」。用 #25 会话数据把两件事分开验证：

### 结论 A：延迟 —— 是，切块占 79.3%
| 组成 | p50 | 占比 |
|---|---|---|
| 等段攒满（段长） | 7.65s | **79.3%** |
| 识别 | 0.32s | 3.3% |
| 翻译 | 1.63s | 16.9% |
| 合计 | 9.64s | |

**硬推理（已被代码确认）**：`live_sub.py:330` `if self._speech_frames >= self.max_frames:`
`_speech_frames` 只数**有声帧个数**。所以凡是被规则②切开的段，切时必然已攒满 15 个
有声帧 → 墙钟 ≥ 15 × 0.51 = **7.65s 是下限，不是均值**。静音帧只会让它更长。
=> p50 恰好 = 7.65s，正是这个下限；62.3% 的段 ≥7.0s。

### 段长直方图（522 段，双峰，证实两种切法并存）
```
2-3s   30 ( 5.7%)  3-4s   65 (12.5%)  4-5s  52 (10.0%)  5-6s  25 ( 4.8%)
6-7s   25 ( 4.8%)  7-8s  130 (24.9%)  8-9s 109 (20.9%)  9-10s 54 (10.3%)
10-12s 27 ( 5.2%)  12-16s  5 ( 1.0%)
```

（两种机制都不常落这里）。**双峰本身就是"两套规则在赛跑"的直接证据。**

### 结论 B：丢字幕 —— **不是**切块的锅
154 条空识别段的真实识别文本（随机 30 条长段）：
```
[ 7.65s] はぁ…はぁ…              [ 9.18s] はぁ、はぁ、はぁ…
[ 8.67s] んじゅるるるっ、じゅるるるるるるっ
[ 7.65s] んぐんぐんぐんぐ、んぐんぐんぐ   [10.20s] んぐっ、んぐっ、んぐぐっ
```
**绝大多数是真·喘息/口音文本，模型没听错，丢掉是对的。**
被丢段文本长度：p50=13 / p90=23 / max=41 字符；>20 字符的仅 28 条，
其中大部分是长拟声重复（`じゅるるるる…`），仍属正确丢弃。

**只找到 2 条"喘息混真话被整段丢"**：
```
[11.22s] …れろれろ…れろれろ…れろれろ…ねろ…また一緒に…
[ 7.65s] ママに乗ったあげよか?…れろれろれろれろれろれろ
```
机制：ASR **对每段只吐 1 个子段**（见下），喘息与真话被塞进同一子段，
平均 logprob 被喘息拉低 → 整段判 low-conf/kana-loop 丢掉，真话陪葬。
属于次要损失，**不是主因**。

### 🔴 新事实：ASR 对每个段都只吐 1 个子段（nseg=1）
```
保留: nseg=1:368      丢弃: nseg=1:154
```
522 段全部 nseg=1，无一例外。子段 `start=0, end=段长`，覆盖整段。
=> **段越长，里面越容易混进性质不同的内容，却只能整体判一个结论。**
这是"长段空率更高"的结构性原因。

### 段长 vs 空识别率（**非单调，别过度解读**）
| 段长 | 段数 | 空识别率 |
|---|---|---|
| <4s | 95 | **15.8%** |
| 4-6s | 77 | 24.7% |
| 6-8s | 155 | **40.6%** |
| 8-10s | 163 | 26.4% ← 破坏单调 |
| ≥10s | 32 | 43.8% |

趋势是"被硬切的长段更容易是空的"，但 8-10s 桶只有 26.4%，
所以**不能说成干净的单调关系**。短段质量更好，因为真静音 = 一句真说完了。

### 逐 segment 丢弃原因 vs 段长
```
<4s     sound-only:10  kana-loop:5
4-6s    low-conf:9  kana-loop:5  sound-only:5
6-8s    sound-only:34  kana-loop:16  low-conf:13
8-10s   kana-loop:19  sound-only:18  low-conf:6
>=10s   sound-only:7   kana-loop:6   low-conf:1
```
sound-only + kana-loop 占绝对多数 = "这段本来就只有喘息"。

## "为什么要切断" —— 根因追到底（2026-09-22 第六轮）

### 实验 1：不切会怎样？（决定性）
把 `smoke90.wav`（实际 60.00s、24kHz 单声道）解码 → 16k → 拼 3 份 = **180s**，
**不做任何切分**一次性喂给 anime-whisper：

```
#0 [   0.00 ->    0.78]   #1 [  30.00 ->   30.70]   #2 [  60.00 ->   60.78]
#3 [  90.00 ->   90.46]   #4 [ 120.00 ->  120.70]   #5 [ 150.00 ->  150.42]
```
**6 段起点全部落在 30.00 的整数倍**，与音频内容无关（同一段内容重复 3 遍，切点照旧）。
=> **Whisper 是 30 秒窗口模型。你不切，它自己在 30.000 秒整硬切，切点你无法预判。**
耗时 12.8s / 180s ≈ 14x 实时。

> ⚠️ 跑这类实验必须先 `import live_sub`：CUDA DLL 注册在模块导入时执行
> （`_add_cuda_dlls()` → `HAVE_CUDA_DLLS`），直接 `from faster_whisper import ...`
> 会报 `Library cublas64_12.dll is not found`。

### 实验 2：翻译侧 token 上限是不是约束？**不是**
`SakuraMT`：`n_ctx=2048`（430 行）、`max_tokens = min(80, max(12, len*3+8))`（449 行）。
实测 368 条有译文的 mt 事件：
- `completion_tokens` p50=**10** / p90=17 / max=47；`max_tokens` p50=56
- `completion_tokens >= max_tokens` 只有 **1 / 368 (0.3%)**，且那条是退化输出（`结结结结…`）

=> **翻译的输出上限当前完全不是瓶颈**，别拿它当"必须切"的理由。

### 两套规则的精确占比（用 audio_s 可判定归属）
- 规则②（有声帧 ≥15）→ 切时已满 15 帧 → **`audio_s ≥ 7.65s` 必然成立**
- 规则①（静音 ≥3 帧）→ 静音分支要求 `_speech_frames < 15` → **`audio_s ≤ 7.14s`**

| 规则 | 判据 | 段数 | 占比 |
|---|---|---|---|
| ② 强制切（兜底） | `audio_s ≥ 7.65` | **315** | **60.3%** |
| ① 静音切（语义） | `audio_s < 7.14` | 197 | 37.7% |
| 归属不确定 | 7.14~7.65 | 10 | 1.9% |

=> **兜底规则变成了主力。** 规则②原本的意图见代码 328-329 行注释：
`must cut while still loud: max_s used to be checked only on silence,`
`so a loud track grew one clip forever and froze ASR` —— 意图是对的，就当兜底用。

### ⭐ 真正的根因：能量阈值分不清"说话"和"喘气"
实测语速（保留段 368 个，总音频 2451.1s，总字符 6345）：

| 段长 | 段数 | 平均时长 | 平均字数 | **语速** |
|---|---|---|---|---|
| 2-4s | 80 | 3.03s | 11.7 | **3.85 字/秒** |
| 4-6s | 58 | 4.62s | 17.6 | **3.80 字/秒** |
| 6-8s | 92 | 7.45s | 18.4 | 2.46 字/秒 |
| 8-10s | 120 | 8.74s | 18.9 | 2.16 字/秒 |
| 10-16s | 18 | 11.48s | 24.3 | **2.12 字/秒** |

**全部保留段平均只有 2.59 字/秒**（正常日语说话 6-8，ASMR 慢速也有 4-5）。
**段长 ×3.8，字数只 ×2.1** —— 多出来的时长里没有话。

**因果链（结论）**：
1. 阈值 0.008 太低 → 呼吸/口水音/底噪全被算作"有声帧"（它们确实在阈值之上，
   所以段内**没有静音帧**，只是"非语音的有声帧"）
2. → 15 帧配额被喘息占满，配额填满速度 ≈ 墙钟速度 → **段必然撑到 7.65s**
3. → 段里只有约 2 秒是真话（16 字），其余是喘息
4. → 静音规则①需连续 1.53s 完全安静，ASMR 里很难出现 → ①只占 37.7%
5. → **79% 的延迟不是"等一句话说完"，是"等喘息把 15 帧配额填满"**

=> 真问题不是"要不要切"，而是**"凭什么判断这一块说完了"**。
现在的判据是**能量**，而能量区分不了说话和喘气，所以切点与语义无关。
