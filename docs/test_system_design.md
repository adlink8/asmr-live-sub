# 测试体系与数据集设计（2026-09-25 定稿）

本文是测试体系的**总设计**：五层各管什么、窗口怎么切、判定阈值、成本与未决事项。
单个场景的文件规范与历史沿革见 [`dataset/README.md`](../dataset/README.md)。

## 0. 设计立场

耳朵管"好用"（延迟、节奏、体感），测试集管听测不出来的三件事：
**翻译对不对**（人工字幕锚点，替用户听日语）、**漏没漏**（missing）、**有没有退步**（可复现数字）。
测试是分层的——180s 场景不验证"听几小时"，小时级由稳定性层与真实场景层负责。

## 1. 五层总览

| 层 | 内容 | 回答的问题 | 判定标准 |
|---|---|---|---|
| ① 回归门 | **27 个 180s 场景**（9 部正常向作品 × 每部 3 个分散窗） | 改动后翻译有没有退步 | 场景语义分比 manifest 基线掉 >5pp 报警 |
| ② 语义测量 | 每场景双口径判定（语义对 / 拦截数据单列） | 翻译对不对、漏没漏 | 意思正确率（LLM 裁判，JA 仲裁）+ missing 率，**分开报** |
| ③ 稳定性 | 60min~3h 原速喂入（soak 素材，无真值） | 连续听几小时会不会坏 | 零段丢失 + 延迟无上漂 + 干净退出 |
| ④ 真实场景 | `realtime_compare.py` 会话对照（待实现） | 实际用起来比人工字幕慢多少、差多少 | 逐条时差中位数/p90 + 语义分 |
| ⑤ 防幻觉 | 6 个负样本（3 真实 + 3 合成，各 30s） | 不该说话时会不会幻听 | 零字幕 = 合格 |

**为什么必须是五层**：180s 场景测不出体感（切块等待占体感延迟大头，p50 4.8s），
长跑测不出翻译质量（soak 无真值），两者不可互相替代。

## 2. ①回归门：窗口设计

### 三等分法

每条被选音轨切三等份，**每份内挑人工 cue 最密的 180s 窗**（平手取最早）：

- 保证三个窗落在头/中/尾，覆盖内容多样性（密集对话、稀疏段落、场景切换）
- 时长统一 180s（2026-09-23 用户指令"时长必须一致"），数字跨场景可比
- 180s 段数 25~34 << seg_q(100) 容量，结构性避开 fast 回放驱逐缺陷

### 作品范围（2026-09-25 核验）

| 状态 | 作品 | 说明 |
|---|---|---|
| 已入库（3 部） | RJ299717、RJ416809、RJ416816 | 现有锚点场景的最密窗即"窗 1"，数字不作废，各补 2 个窗 |
| 新增（6 部） | RJ01449384、RJ01463510、RJ01467825、RJ01497366、RJ01527130、RJ01528043 | 全部 nsfw=False、VTT 时间戳人工字幕已核验；RJ01467825/RJ01528043 是套装，按嵌套内层号（RJ324799/RJ01521586）记 track |
| 搁置（9 部成人向） | zh-corpus 内其余 | 等正常音频全流程验收后由用户点名启用；启用前置件=本地裁判模型（见 §6） |
| 踢出 | RJ401391 | LRC 与音频不对应（台词 vs 纯声响），配对全是垃圾对 |

多轨作品取**人工 cue 最多的音轨**（沿用现有规则）。

### 命名与字段

```
scene_asmr<workid>_t<track>.human_zh.json      人工中文（汉化组/投稿 LRC/VTT 拆出）
scene_asmr<workid>_t<track>.live_ja.json       GPU 实跑日文（翻译实验输入，非真值）
scene_asmr<workid>_t<track>.judge_input.json   裁判输入（人工 cue 为分母、时间重叠配对）
scene_asmr<workid>_t<track>.semantic_judge.json 裁判 verdict（带 kind，双口径）
```

manifest 每场景新增两个字段：`window_pos`（start/mid/end）与 `track_id`——
将来可回答"安静段落是不是更容易出问题"。

### 预期收益

语义样本量 66 对 → 约 **600 对**（×9）；报警分辨率从 ±5pp 提到约 ±1.5pp。
成本：27 场景 GPU 实跑约 2 小时（过夜后台），判分 API 费用忽略不计。

## 3. ②语义测量：双口径纪律

- **语义分母**：意思类 cue（对白/叙述）。裁判判 correct/partial/wrong，歧义以日文原文仲裁
- **拦截数据单列**：拟声/倒计时类 cue（kind 标记），不计入语义分母，但**连判对的一起剔**——
  只剔判错的是按结果挑数据
- **missing**：无任何 ASR 段覆盖的人工 cue（"该显示没显示"），锚点轨独有度量，随场景单独报
- 碎句不影响语义：一条人工 cue 可由多个 ASR 段聚合（时间重叠配对，`tools/build_anchor_scene.py`）
- 裁判会错且 n 小：数字读作估计与退步报警，不读作精确真值

## 4. ③稳定性层

- 跑法：`tools/run_long_eval.py`，realtime 原速喂入（fast 模式仅用于压测，结论一律不采信——
  fast 段数锁 101、realtime displayed 锁 50，两个回放 harness 缺陷用户已决策**不修**）
- 已有证据（2026-09-23）：60min 原速喂入 356 段零缺口、348 条字幕、零报错，与矩阵轮复现重合；
  10 分钟分桶延迟无上漂（后半程更低为内容因素）
- 扩展项：跑一次 2~3h（改参数即可），把小时级证据延到实际收听时长；
  顺带做全轨 missing 分析（纯几何计算，不需要判分 API）

## 5. ④真实场景层：realtime_compare（待实现）

**原则：不碰浏览器。** asmr.one 播放器显示的字幕就是语料库里的 LRC/VTT，
时间轴以本地文件为准（不怕网页改版/反爬）。

```
用户正常听（外放/耳机，live 环回采集，真实使用状态）
  → WorkLog 逐条记录上屏墙钟时间 + ja/zh
  → tools/realtime_compare.py：
      读作品人工字幕时间轴
      → 自动对齐起点（本地 zh 模糊匹配人工字幕行搜最优偏移；支持人工指定）
      → 每条 cue：应在 T_cue 出现 vs 实际 T_local 出现 → 逐条时差
      → 本地 zh vs 人工 zh 逐对打包 judge_input → 语义正确率
  → 输出：时差中位数/p90、覆盖率、语义分
```

使用纪律：对比会话不暂停/不拖进度条（对齐容忍小幅抖动，不容忍跳轨）。
先做事后版，实时滚动显示（tail 模式）为可选第二阶段。
