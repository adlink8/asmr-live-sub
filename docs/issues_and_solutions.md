# 系统问题与架构排查全景复盘文档

本文档归档记录系统在搭建、评测与长期运行过程中遇到的全部核心工程问题、底层现实病因、解决方案及验证数据。

---

## 1. 硬件运行环境基线

- **CPU**: AMD Ryzen 7 7840H / 8845H (16 线程，内置 Radeon 780M 核显)
- **独显 (dGPU)**: NVIDIA GeForce RTX 4060 Laptop GPU (8GB GDDR6 VRAM)
- **操作系统**: Windows 11 (23H2 / 24H2)
- **显示配置**:
  - 内置屏幕: 2560x1600 165Hz (Windows 逻辑缩放 150%，逻辑分辨率 1707x1067)
  - 外接屏幕: HDMI 连接 F24G40F (1920x1080 165Hz，逻辑坐标从 X=2560 延伸至 X=4480)
- **核心推理栈**:
  - 语音识别 (ASR): `anime-whisper-ct2` (CTranslate2, CUDA fp16)
  - 机器翻译 (MT): `Sakura-7B-Qwen2.5-v1.0-IQ4XS` (llama.cpp, CUDA 33 层全卸载)

## 2. 核心问题复盘清单

### 问题一：独显显存被系统霸占，大模型无法上卡

- **故障现象**：
  启动模型时频繁触发 CUDA OOM（内存溢出）崩溃；退回 CPU 推理后，单句翻译延迟高达 **2.4s ~ 3.2s**，实时字幕严重积压滞后。
- **现实病因 (Why)**：
  笔记本此前处于【独显直连】模式，Windows 桌面窗口管理器（`dwm.exe`）、浏览器硬件加速、壁纸引擎及外接显示器全部挤占独显，开机空载显存占用高达 **3682 MiB**（剩余仅 4.5 GB）。
  `Sakura-7B IQ4XS` 权重需 4.85 GB，加上 Whisper 的 1.05 GB，显存赤字超 1.4 GB。
- **解决方案**：
  1. 机械革命控制台中将 GPU 工作模式由【独显直连】切换为【混合输出】；
  2. 重启后由 AMD Radeon 780M 核显接管桌面与日常应用渲染，独显桌面占用从 **3682 MiB 骤降至 1362 MiB**，净释放 **2.32 GB 显存**；
  3. 配置 `torch/lib` 与 `llama_cpp/lib` 动态链接库路径，成功激活 `llama_cpp` 的 CUDA 支持。
- **验证结果**：
  - 独显常驻总占用控制在 **7.26 GB / 8.18 GB**，零 OOM 溢出；
  - Sakura-7B 33 层完整卸载至 GPU Tensor Cores，单句翻译耗时从 **2.37s 压缩至 0.47s**（短句 0.14s~0.25s），提速超 400%。

### 问题二：Windows 任务管理器中 GPU 利用率仅显示 8%

- **用户疑问**：
  模型显存吃满了 7.6GB，为什么任务管理器中 GPU 利用率只有 8%，显卡是不是没出力？
- **现实病因 (Why)**：
  1. **统计通道错位**：任务管理器右上角图表默认显示为 **`3D` 引擎**（统计 DirectX/游戏光栅化渲染）。AI 模型走的是 **`CUDA / Compute` 引擎**，在 `3D` 下只能看到约 8% 的桌面窗口合成渲染；
  2. **突发性脉冲计算机制 (Burst Compute)**：
     - 人类说话 4 秒期间，仅声卡在录音，GPU 处于 **0% 待命**；
     - 说话停止瞬间，Whisper 耗时 0.3s + Sakura 耗时 0.2s，GPU 在 **0.5 秒内极速脉冲计算完毕**；
     - 在 4 秒的语流周期里，GPU 实际只工作了 0.5 秒，其余 3.5 秒都在等待音频输入。时间加权平均利用率自然稳定在 **8% ~ 12%**。
- **技术结论**：
  在显卡显存已满载的前提下，时间平均算力利用率低恰恰说明**单句推理速度极快（百毫秒级秒杀）**，算力高度富余，显卡温度稳定在 58°C，功耗仅 20~25W。

### 问题三：启动后屏幕“没有任何反应、无字幕条”

- **故障现象**：
  在 AI 助手终端执行启动命令后，后台日志显示每句话都在正常识别翻译，但物理屏幕上空空如也，看不到任何悬浮窗口。
- **现实病因 (Why)**：
  1. **Windows 11 桌面会话隔离 (Session/DWM Isolation)**：
     通过 IDE / AI 助手后台终端拉起的子进程属于非交互上下文，Windows 会将该子进程创建的 Tkinter GUI 窗口锁死在不可见的虚拟会话中，DWM 合成器拒绝将其绘制到物理屏幕上；
  2. **多屏幕逻辑坐标错位**：
     系统接有双显示器（笔记本主屏 1707x1067，外接 HDMI 屏 1920x1080）。旧代码只计算了主屏宽度（`x = 1707 - 1120 - 50 = 537`），将窗口直接扔在笔记本主屏右下角。若用户主要注视外接屏，外接屏物理上为空白；
  3. **无边框窗口 Z-Order 层级丢失**：
     Tkinter 的 `overrideredirect(True)` 使得窗口成为无所有者的 `WS_POPUP` 窗口，在 Windows 11 下极易被全屏浏览器（如 asmr.one / Edge）覆盖。
- **解决方案**：
  1. 重写 `SubtitleWindow` 类（该类 2026-09-22 起位于 `livesub/gui.py`）：
     - 利用 Win32 API `EnumDisplayMonitors` 枚举全部物理屏幕坐标；
     - 检测到外接屏（`monitors > 1`）时，自动将窗口定位至外接屏幕底部中央（`X = 2560 + (1920 - 1120) // 2 = 2960`）；
     - 为画布增加 1px 亮蓝色高对比度边框（`#3b82f6`）防视觉隐形；
     - 注入 Win32 原生 `SetWindowPos(HWND_TOPMOST)`，每次轮询时强行置顶；
       ⚠️ 2026-09-22 核查：该调用此前一直静默失效——原文件没有模块级 `import ctypes`，
       `_force_topmost()` 里的 `ctypes.windll` 抛 NameError 被裸 `except` 吞掉，
       实际只有 tkinter `-topmost` 在工作。拆分时已在 `livesub/gui.py` 模块级补上
       `import ctypes` 修复，本条承诺现在才真正生效（效果待实盘验证）；
     - 添加 `WS_EX_APPWINDOW` 扩展样式，使窗口常驻任务栏以便随时激活；
  2. 固化 [`start.bat`](file:///d:/ADLINK/asmr-live-sub/start.bat)，要求通过 Windows Explorer 资源管理器原生双击启动，彻底打破会话隔离。

### 问题四：音频通道漂移与静音死锁

- **故障现象**：
  首次启动后字幕条停留在 `listening...`，不再滚动出字。
- **现实病因 (Why)**：
  启动初期系统默认音频绑定到了蓝牙耳机（OPPO Enco Free4）；随后蓝牙断开，Windows 声音输出回退至有线接口（Senary Audio）。但旧 Python 进程依然死锁在已失效的蓝牙音频端点上，持续捕获全 0 静音包。
- **解决方案**：
  编写非阻塞回调探针，枚举并检测各输出端点的实际发声信号强度（峰值电平与 RMS），确认 `[35] 耳机 (Senary Audio)` 存在有效声音（peak=0.1858），重定向并重启监听进程。

### 问题五：长音频与持续掏耳水声导致“死循环幻觉”

- **故障现象**：
  在 180 秒持续掏耳水声测试中，未切块的 Teacher 大模型出现连续 7 次重复打印无意义日常台词（死循环幻觉）。
- **现实病因 (Why)**：
  Whisper 等自回归模型在面对长时间连续非言语高频噪声（流水声、摩擦声）且缺少声音边界时，注意力机制因缺少音素引导而退化为自发语言先验，陷入重复文本幻觉。
- **解决方案**：
  1. 在 `Segmenter`（2026-09-22 起位于 `livesub/audio.py`）中引入**策略 2 自适应阶梯衰减切块 (Adaptive Ladder Decay)**：
     - 前 3 秒要求连续 2 秒静音以保护完整句子；
     - 超过 3 秒后，仅需 1 帧（~0.5s）停顿即刻切断，单段绝对上限锁死为 5.0 秒，杜绝长段噪音堆积；
  2. 结合文本后置过滤器（`_MOAN` 拟声表、`HALLU_RE` 致谢/订阅幻觉正则、`_LOOP_UNIT` 循环字块正则），将掏耳水声直接转写为真实拟声词（如 `ズズズズズ…`、`じゅるるる…`）。
     - 数据来源：`logs/benchmark_runs/accuracy_report_official_mika.md`（黄金真值 `gt_official_random.json`，jiwer 测定）。
     - 幻觉多字率 (Ins) **0.2%**（≤3% 安全线内）、替换错字率 (Sub) **1.63%**。
     - ⚠️ **2026-09-22 事后复查更正**：本节旧版引用的"翻译语义对齐度 **100%**"是**自比自恒等式，不是测量**——
       生成真值时 align 脚本把同一次实时运行的 mt 译文直接抄进了真值文件，评分时再拿它比 live 译文，必然 100%。
       该指标已废除（align 不再抄译文；evaluate 的 MT 指标改为必须 `--mt-ref` 独立参考，否则判"不可评"）。
       **2026-09-22 二次修正（质量参考）**：teacher 参考（39.62%）也不干净——时间戳不可靠且含 beam=5 退化段。
       已由 `tools/build_quality_reference.py` 取代：同一 Sakura 模型贪心解码+长输出的离线精译，
       真值/参考收进 `dataset/`（标准索引 manifest.json）。
       **2026-09-22 三次修正（双侧剔除）**：v3/v4 的 83.71%/16.29%/14.43%/71.48%
       没有消费 gt 的 excluded 字段——拟声/低置信段的 official_ja 抄的是 live 自己的文本，
       双边自匹配把分母从 415 灌到 485，指标偏乐观约 3 个点。当前有效口径
       `logs/benchmark_runs/accuracy_report_20260922_v5.md`（dataset 版 gt/ref）：
       ASR 80.96% / CER 19.04% / 吞字 16.87% / 幻觉 0.24%；
       MT 实时 vs 离线精译相似度 **71.08%**（差距分解：约 20.2 分识别损伤传导 +
       约 8.7 分翻译配置退化，识别侧是绝对大头，拆解见 tools/README.md）。
     - ⚠️ 同一份报告里**吞字漏识别率 (Del) 14.26%，超 5% 安全线近 3 倍**，ASR 字符错误率 (CER) 16.09%。
       漏字主因是切块斩断词尾（见问题七），与幻觉不是同一个病——引用 0.2%/1.63% 时必须同时引用 14.26%，否则是选择性呈现。
     - 另注：该 16:21 报告与 17:22 被覆盖重跑过的 `custom_random_talk.jsonl` 不是同一次配对，
       历史数字已不可用当前文件复现；重新配对后的数字见上一条。
     - 注：策略 2 的"单段绝对上限 5.0 秒"来自 `start.bat` 传入的 `--max-s 5.0`；代码默认 8.0，
       且 baseline 策略下 `max_s` 只数有声帧、名不副实（见问题七）。

### 问题六：运行时漏句子，切歌换轨时加载慢或不翻译 —— ⚠️ **未修复，两个”解决方案”均未落地**

- **故障现象**：
  日常播放中部分短句（如相槌）丢失；切换新音频轨道后，字幕需等待数秒甚至十几秒才开始显示，较轻柔的音频甚至全程不翻译。
- **现实病因 (Why)**：
  1. **一刀切短句丢弃硬门槛 (`MIN_SEG_S`)**：
     底层诊断日志证实，单次运行会产生数百次 `seg-drop: too-short` 丢弃事件。
     **2026-09-22 当日日志（`logs/work-20260922.jsonl`）复核：331 次 seg-drop，voiced_s 全部为 0.51s (203 次) 或 1.02s (128 次)**——
     日语日常口语和 ASMR 中大量核心短句（「はい」「先生」「大丈夫？」「すき」「うん」「わかった」「どう？」）发音均在 0.5~1.0 秒内，全部被此门槛无声抹杀。
     （本文档旧版曾记录”216 次”，为更早会话的数据；问题至今存在且计数更高。）
  2. **动态能量门限 (Gate) 滑动窗口滞后**：
     门限基于 6 秒历史音量滑动窗口调整。若前一段音频音量较大，门限被撑高至 `0.04 ~ 0.06`；切换至轻柔新歌时，旧音量残留导致新歌弱人声（电平仅 `0.01~0.02`）在前几秒被全数误判为”静音”，直到历史窗口排空后才恢复感知。
- **”解决方案”的真相（2026-09-22 代码核查）**：
  1. ~~将 `MIN_SEG_S` 从 `1.5s` 下调至 `0.4s`~~ —— **未实施**。代码现值仍为 `MIN_SEG_S = 1.5`（单文件时代为 `live_sub.py:31`，拆分后为 `livesub/config.py`）。
  2. ~~能量门限状态机增加”静音快速归零复位”~~ —— **未实施**。`_update_gate` 只有 asmr/loud 双模滞回，没有任何检测到 1 秒静音即复位门限的逻辑。
  两条都停留在纸面。实盘一直跑的是 `MIN_SEG_S=1.5`。
- **为什么不直接改（取舍）**：
  `MIN_SEG_S=1.5` 是 2026-09-20 从 0.8 **抬上来**的：当时 788 个 <1.5s 碎片占段数 51%，抬门槛后碎片归零、空识别率从 68% 降到 ~24%。
  降到 0.4 能救回相槌，但会把喘息碎片还给我们——除非后端文本过滤器能干净地处理它们。
  **这是”漏句子”与”浪费算力+掺入噪音”之间的取舍，需要实测数据支撑，不能拍脑袋。**
  正确的下一步是先量化：331 次被丢的 0.51/1.02s 段里，ASR 实际能识别出多少有效内容
  （用 `--replay` 离线回放 + 临时调低 `MIN_SEG_S` 即可测得，不需要新代码）。

### 问题七：字幕延迟 ~9.6 秒 —— 延迟主体是”等段攒满”，不是算得慢（2026-09-22 新增）

- **测量方法（可信口径）**：按 `seg_id` join `asr` 与 `mt` 事件（会话 #25，368 条配对），
  **端到端延迟 = 段长 + 识别 + 翻译**：

  | 组成 | p50 | 占比 |
  |---|---|---|
  | 等段攒满（段长） | **7.65s** | **79%** |
  | 识别 asr | 0.32s | 3% |
  | 翻译 mt | 1.63s | 17% |
  | **合计** | **9.64s** | p90 12.41 / max 16.98 |

- **⚠️ 日志陷阱**：`[sub]` 行和 `result_q` 里的 `dt` 只是 `asr_s + mt_s`，**不含段长**。
  只看日志会得出”很快”的错误印象。本文档性能表旧版”端到端 4.50s”即此类口径的产物。
- **根因**：段长 p50 恰好 = 7.65s = 15 帧 × 0.51s = `max_frames`（`int(8.0/0.51)`）。
  baseline 策略下 `max_s` 名不副实——`_speech_frames` **只数有声帧**，喘息/呼吸声都算”有声”，
  15 帧配额被喘息填满，段必然撑到上限才吐。实测 62.3% 的段 ≥7.0s，最大 15.30s。
  自适应/阶梯策略（`adaptive`/`hardcap`）的 `time_up` 是墙钟口径，`--max-s 5.0` 时上限真实生效；
  **但实盘大量跑的是 baseline + 默认 8.0，配额口径的 bug 就在这条路上**。
- **旁证**：基准报告 `logs/benchmark_runs/accuracy_report_official_mika.md` 的吞字漏识别率 14.26%
  （超 5% 安全线）与”切点与语义无关”是同一病因的两面。
- **另一处取整 bug**：`hang_frames = max(1, int(2.0/0.51)) = 3 帧 = 1.53s`，`hang_s=2.0` 从未真正生效（取整丢 23%）。
- **取舍（未动手）**：想字幕快 → 必须更多地在句中切断；想断句准 → 字幕必然更慢。**没有免费午餐。**

## 4. 日常标准启动与操作 SOP

**代码结构（2026-09-22 由单文件拆分为 `livesub` 包，入口不变）**：

```
live_sub.py          薄入口 + 兼容层（start.bat 与 import live_sub 的脚本都走这里）
livesub/config.py    路径/环境变量/调参常量/CUDA DLL 注册（必须最先导入）
livesub/logging.py   LineLog（控制台+文件）/ WorkLog（JSONL 事件 trace）
livesub/filters.py   文本过滤层：幻觉/假名循环/sound-only/low-conf/拒答
livesub/audio.py     FrameBuffer / 重采样 / Segmenter 能量门切块 / 设备枚举
livesub/models.py    ASR 加载 + Sakura/NLLB/Qwen 三个 MT 后端
```

1. **一键启动**：
   在资源管理器中直接双击根目录下的 [`start.bat`](file:///d:/ADLINK/asmr-live-sub/start.bat)；
   - 内部已预置最佳参数：`--model anime --mt sakura --mt-ngl 99 --strategy adaptive --max-s 5.0 --hang-s 2.0`。
2. **多屏指定（可选）**：
   - 默认会自动识别并优先放置在外接显示器；
   - 若想强制固定在笔记本主屏，可传参：`start.bat --screen 0`；
   - 若想强制固定在外接大屏，可传参：`start.bat --screen 1`。
3. **窗口交互**：
   - 鼠标按住字幕条任意位置即可随意拖拽；
   - 按 `Esc` 键或直接关闭控制台终端窗口即可完全退出。
